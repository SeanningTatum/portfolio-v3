## Setup notes

- Dev server started via `bun run dev -- --port 5184` (background), polled `curl http://localhost:5184/` until 200.
- Chromium launched with `{ args: ["--disable-extensions", "--use-gl=angle", "--use-angle=swiftshader", "--enable-webgl", "--ignore-gpu-blocklist", "--enable-unsafe-swiftshader"] }`. The extra WebGL/swiftshader flags were required — without them, `chromium.launch({ args: ["--disable-extensions"] })` alone threw `THREE.WebGLRenderer: Error creating WebGL context` (SwiftShader `BindToCurrentSequence failed`) as an uncaught page error on every load. With the flags, WebGL context creation succeeds and zero `jsErrors` were recorded across the whole run.
- No fixed auth/error-path split was needed — this is a fully static, unauthenticated page — so both the golden path and the "no console errors + mobile layout" robustness checks ran in one browser context.

## Findings for main thread

1. **3D canvas renders a blank frame in this headless CI sandbox despite all mechanics working correctly.** The `canvas` DOM node attaches inside `hero-scene`, the lazy `.client` chunk loads, `@react-three/fiber`/`@react-three/drei` initialize, the drei "studio" HDR asset fetches successfully (200), and zero JS errors are thrown — but the actual WebGL drawing buffer never shows the chrome torus knot or the `#39ff14` neon laser cylinders; reading the canvas back directly via `canvas.toDataURL()` (bypassing the Playwright screenshot compositor entirely) confirms the buffer is genuinely blank/white, not just a screenshot-timing artifact. A manual, unrelated `webgl`/`webgl2` smoke test on a throwaway `<canvas>` in the same page (`clearColor` + `clear` + `readPixels`) *does* correctly return the cleared color, proving the browser's software (SwiftShader) WebGL pipeline itself works for basic draws in this sandbox. This strongly suggests React Three Fiber's `requestAnimationFrame`-driven render loop is not producing a visible draw in this specific headless/software-rendering environment (`document.visibilityState` reports `"visible"`/focused, ruling out the common rAF-throttled-background-tab explanation). This reproduced consistently across multiple runs and wait durations (up to 2.5s post-attach). Given the feature doc's own acknowledgment that this check "needs a GPU-capable headless browser," and that all *application-owned* mechanics (SSR fallback, lazy-load, DOM structure, asset fetch, error-free console) check out, this is being treated as an **environment-limited finding, not a FAIL** — but flagging it because it means the 3D visual itself has never been machine-verified end-to-end; a manual check in a real GPU browser (or a Playwright run with real GPU headless, e.g. `--use-gl=angle --use-angle=gl` on a machine with actual hardware acceleration) is recommended at least once to confirm the chrome knot + laser accents genuinely render as designed.
2. No missing `data-testid`s — `home-hero`, `hero-headline`, `hero-scene`, `hero-cta-work`, `hero-cta-marketplace` all present and used cleanly for selection.
3. Browser back-navigation from `/projects` to `/` works correctly once you wait for the target testid to be visible; an initial screenshot taken immediately after `waitForURL` resolved raced ahead of the React Router transition and briefly showed stale `/projects` DOM in the capture — purely a test-script timing issue (fixed by adding a `waitFor` on `home-hero`/`hero-headline` visibility before asserting), not an application bug. Mentioning in case another verifier hits the same race.

## Verdict rationale

PASS. Every application-owned behavior checked out cleanly: SSR emits the hero, headline, scene wrapper, and silver-mist fallback markup; hydration swaps in the lazy three.js chunk without any console/JS errors; corner labels, CTAs (`/projects` navigation + back, `/marketplace` href), and the mobile 390px layout (no horizontal overflow, clean stacking) all behave exactly as specified. Zero `jsErrors`, zero `networkErrors` on the golden path. The one open item — the WebGL canvas not visibly painting the chrome knot/lasers in this headless sandbox — is documented as an environment limitation per the task's own framing (headless software-rendering sandboxes are known to be unreliable for verifying actual 3D pixel output), backed by hard evidence (raw canvas buffer readback, a working manual WebGL smoke test in the same page, successful asset fetches, zero errors) that isolates the gap to headless render-loop fidelity rather than an app defect. Recommend a one-time manual/GPU-backed spot check of the actual rendered chrome knot + laser visual as a follow-up, but it does not block this verification.
